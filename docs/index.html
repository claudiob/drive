Rails 8.1 and up

Recourse

The CRUD screens a scaffold doesn't give you, for one word in routes.rb.

A scaffold gets you seven actions and a page you would not show anyone. This replaces the views and the controller with screens meant to be used — sorted, filtered, searched, paginated, nested, and formatted by what each column actually holds.

config/routes.rb
resources :posts
recourses :posts
Gemfile
gem 'recourse', '~> 4.0'

Version 4 is a rewrite, and continues the version line of the recourse gem it grew out of. It follows Semantic Versioning, so pinning the major means bundle update never crosses a breaking change.

The problem

A scaffold is not meant to ship

In the video on rubyonrails.org, David builds and posts a blog in thirty minutes. He is careful about how his products look, and even so the blog you get is ugly — ugly for a scaffold. He says as much: “It's quite basic, to put it mildly. This scaffold interface is not meant to ship to production.”

The larger loss is that it shows none of the potential. Rails ships with a great deal that a scaffold never puts on screen. So what would this app need before it is ready for production — at least for those of us who mostly want to do CRUD on a model?

The idea

Convention, all the way down

The convention here is CRUD itself: everything is a resource. Write resources :posts and Rails already knows which model, view, helper and controller to expect. So once the model exists, why ask you to write the view, the helper and the controller — if what you want is the conventional one?

If you agree with the fifteen above about what conventional means, that is the whole of it. Here is the recipe.

1

Change resources to recourses

For whichever resources you want screens for. Then delete the controllers and views the scaffold wrote.

config/routes.rb
Rails.application.routes.draw do
  recourses :posts
  recourses :comments
end
Gives you 01 02 03 04 08 14 15
2

Nothing

There is no step two. The screens are served from the gem, so there is no generated code to keep, and nothing in your app to maintain.

3

Index the columns worth sorting, filtering and searching by

An index is the only honest signal a schema carries about which column identifies a row rather than describing it, so that is the signal read here. No index, no sorting.

Gives you 09 10 11
4

Use the right column types

A decimal is rounded to its own scale, a price wears its currency, a percentage its sign. An enum becomes a badge on the page and a menu in the form; a foreign key becomes a menu of the records it points at, or a field to type into where there are too many to list.

Gives you 05 06
5

Seed it

$ rails g recourse:seed && rails db:seed

Twenty-five rows per model, each value drawn to the shape of its own column — inside whatever length its validator states, and inside the column's own limit.

Gives you 07
6

Declare both sides of an association

A has_many with the belongs_to facing it, and a counter cache where you want the number on the tab. Or let the generator write them, along with the migration and the nested route.

$ rails g recourse:counters && rails db:migrate
Gives you 12
7

Encrypt what should not be read over a shoulder

app/models/contact.rb
class Contact < ApplicationRecord
  encrypts :phone, deterministic: true
end

An encrypted column never reaches a table at all. On the record's own page it arrives as one asterisk per character, with a Show beside it — so a screenshot discloses nothing nobody asked to see.

Gives you 13
The cost

Two things

What you giveWhy
one wordresources becomes recourses in config/routes.rb.
correct modelsYour models are what decide the convention these routes and screens follow. Everything is read from them.

The gain is that the behaviour lives in one place. Sorting by a column is conventionally earned with an index — so if you don't add one, there is no sorting. It is the same rule everywhere, and it is a rule rather than a setting.

Everything you can change

A short list, and it is the whole list

Almost all of this arrives without customising anything. Some of you will want to anyway, so here is what there is.

This is not to say your app cannot be your app. Use resources and every bit of it is yours to shape. Reach for recourses and the conventions have been taken for you — which is the trade, and why the list below is as short as it is.

On a model

MethodWhat it decides
recourse_labelthe column a record is named by, in a breadcrumb and anywhere else it is referred to
recourse_hiddena column, or a list of them, no screen shows
recourse_timestampswhich of created_at and updated_at a table ends with
recourse_ordera default order other than by id
app/models/post.rb
class Post < ApplicationRecord
  def self.recourse_label = :title
  def self.recourse_hidden = :body
  def self.recourse_order = 'published_on desc'
  def self.recourse_timestamps = %i[updated_at]
end

In a row partial

To decide what the table itself looks like, write the row. The record arrives as a local named after the model, and three helpers are yours.

HelperWhat it draws
columnone column — the heading in the header row, your block in every row after it
sort_headera heading that sorts by its column
search_highlighta value with the searched text marked
app/views/posts/_row.html.erb
<%# locals: (post:) -%>
<%= column header: sort_header(:title) do %>
  <%= link_to search_highlight(post.title, :title), post %>
<% end %>

<%= column header: 'Words' do %>
  <%= post.body.split.size %>
<% end %>

Once, for the whole app

If you would rather it were not blue:

config/initializers/recourse.rb
Recourse.color = :purple

And if the screens need a before_action of your own — authentication, most likely — reopen the controller they all inherit:

app/controllers/recourses_controller.rb
class RecoursesController < Recourse::BaseController
  include Authenticable
end

That is the entire surface. Everything else the gem defines is its own working, and moves without notice.

Generators

  • rails g recourse — a model, a migration, a route, seeds
  • rails g recourse:counters — both sides of an association
  • rails g recourse:seed — rows for every resource drawn

Built on

  • Active Record validations, for every rule a field shows
  • Turbo, for frames, refreshes and the warning before a delete
  • Ransack and Pagy, for sorting, filtering and pages

Needs

  • Rails 8.1 or newer
  • Ruby 3.2 or newer
  • A model worth putting on a screen

Recourse — because the second time round, it should already be built.
